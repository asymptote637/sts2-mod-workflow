# 从需求到可运行 Mod

## 1. 选择实现入口

STS2 使用 C#／Godot，当前项目以游戏内置 Mod Loader、Harmony 和 GDScript 资源为入口。先检查实际游戏安装中的程序集、PCK 和原生库，再选择匹配的 .NET／Godot 版本。不要沿用 STS1 的 Java／ModTheSpire 打包流程。

新建项目可参考 [Alchyr/ModTemplate-StS2](https://github.com/Alchyr/ModTemplate-StS2)，结合当前分支的 manifest 与初始化 API。以本机游戏内的类型和已运行的最小 Mod 为编译依据；模板更新不自动证明某个游戏版本兼容。

先形成一个最小可加载 Mod：manifest、入口 DLL，资源型 Mod 再加入 PCK。入口使用当前版本提供的初始化属性／回调；资源路径、程序集名称和 Mod ID 保持一致。先证实初始化日志、一个最小 UI 或模型挂载，再扩展功能。

## 2. 冻结产品范围

将需求区分为外观表现、牌组／数值／机制、UI／工具。表现扩展可保留职业身份、牌组、伤害、随机数和原生存档，只改人物、头像、名字、语音及演出；玩法改动则单独设计存档和联机约束。

`affects_gameplay` 应与实际实现相符。不要为了适配某个筛选器而把有玩法影响的 Mod 标成纯表现，也不要将历史项目的“不改玩法”设为用户新需求的限制。

## 3. 资源来源与接入

建立源清单：来源链接、Git commit／blob、原始 SHA-256、角色／皮肤／模型 ID、原作配置、资源类型与许可。下载缓存和运行派生资源分开。代码许可不能自动授予字体、原声和游戏素材的再分发权。

角色资源按实际类型处理：

- **Spine**：检查 skeleton、atlas、纹理是否属于同一版本，使用游戏实际提供的 Spine 扩展，分别验证战斗／房间／UI。
- **Cubism**：检查 model3、moc3、纹理、physics、expression、motion 和 mask 引用。GDExtension 与 Cubism Core 的平台、CPU 和许可证一起入包。
- **Godot 导入资源**：PCK 需包含运行时真正读取的导入结果与引用映射，不能只放源 PNG／音频后假设运行时会导入。
- **原声／字幕**：根据真实语言的时间线、内容和录音终点匹配；表情、身体、口型可以并行，不能仅按名称数字后缀串接。停止、换人和退出时复位播放器及字幕。

新角色建立稳定 ID；目录从单一配置源生成。档案、语音、头像、动作和生命周期达到既有交付标准后才计入数量。角色数量变化时复查分页、渲染网格、安装器、默认列表和全量测试中的固定数量。

### Cubism 的数量头问题

本项目实际遇到 motion 的 `CurveCount`、`TotalSegmentCount`、`TotalPointCount` 与曲线数据不符，连续加载触发原生越界写入。修复派生运行文件的计数并保留原始下载文件／曲线；报告原始和派生哈希。对新模型先核对数据，再做原生加载与全目录循环测试。不能只凭一个模型单次加载通过判断目录安全。

## 4. 原生桥接与演员归属

从实际调用入口确定玩家、对局和生命周期，尽量使用当前版本的原生资源加载器、场景、动画与传输层。

- 大厅偏好可以按单人／多人保存；开局时按本局及玩家冻结外观。读档和续局读取该局快照，大厅改选不能回写旧局。
- 联机按已验证发送者处理消息；同职业队友仍是不同玩家。未参与通道的玩家保留其合法默认表现。
- 战斗、只供展示的过场、商店、篝火、续局和最终结算分别持有演员，离场后清理外部节点、信号、位移和采样节点，恢复原生身体。
- 检查动作 Mod 是否实际启用及逐牌规则，明确身体动作和特效由谁驱动，避免重复旋转、重复攻击特效或同时抢占同一动画轨。

## 5. UI 与性能

按可见窗口验证人物比例、文字、输入、焦点、点击和透明容器。SubViewport 中的正确画面不能替代原生窗口里的控件交互。屏幕采样特效检查相机位移、缩放、MSAA、先行采样、停止和死亡；在目标平台实际使用的渲染后端验收。

Cubism 部件的高 z 值可能穿透宿主 UI。需要保留内部绘制次序但限制在人物画布内时，可将部件绘制排序转换为同层兄弟顺序，测试中加入真实商品面板等遮挡层。

按需加载与有界缓存优先于全量预载。缓存淘汰只移除缓存引用，活跃演员／播放器保留自己的资源。分别记录首次加载与热调用；不要把 release 构建不可用的内存计数当作 0。

转场卡顿应拆分菜单启动预载、确认后的淡出、资源加载、模型首载和释放。使用原生同一串行队列提前加载时，确认没有重复建局、改写 RNG 或额外延长淡出。性能对照使用相同 fixture 和同样的游戏版本，单独说明与完整手动流程的关系。

## 6. 验证与数据保全

修复前保存最小复现、旧包／哈希、截图与日志；按改动选择以下层级：

| 层级 | 验证什么 | 结论限度 |
| --- | --- | --- |
| 构建与静态资源 | 编译、路径、来源锁、manifest、平台原生库 | 不能证明实际画面正确 |
| 状态／协议 fixture | 偏好、逐局快照、玩家、读档、发送者隔离 | 不能代替双机器 Steam 传输 |
| 独立引擎 | 脚本、资源、语音、模型、动作与清理 | 使用游戏扩展时注明运行环境 |
| GPU 画面 | UI、比例、采样、图层和窗口组合 | 需要查看实际输出图 |
| 原生桥接 | 游戏真实节点、回调、资源加载和生命周期 | fixture 与实际游玩分别记录 |
| 安装／回退 | 逐文件读回、备份、依赖和数据变化 | 备份范围以安装记录为准 |
| 实际流程 | 手动买卖、完整通关、双机／重连 | 只记录实际完成的流程 |

原生 QA 前保存当时最新的存档／设置／外观文件及清单、哈希。隔离真实菜单输入，阻断实际建局、读档、保存与重载计数；需要测试真实持久化时使用明确隔离的测试数据。结束后检查旧文件未变、没有新增存档、临时 Mod 已移除。

报告写入被测产物哈希。同一项目的构建、GPU 测试、原生测试和安装常共享工作文件，不并发覆盖。纯文档或包装变化只验证对应范围；若核心 DLL／PCK 变化，就更新其相关运行验证。

## 7. 版本交付

同步 manifest、C# 项目版本、初始化日志与用户文档。交付状态至少说明源码、构建和实际安装版本，以及哪些测试绑定了哪些哈希。已验证产物进入 [打包与 GitHub 流程](packaging-and-github.md)。
